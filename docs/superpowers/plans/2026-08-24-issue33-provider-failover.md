# Phase — LLM Provider Failover (issue #33)

Approved 2026-08-24 with Иосиф Правец.

## Goal

Цепочка LLM-провайдеров в конфиге с автоматическим failover при сбоях и возвратом на приоритетный провайдер после восстановления. Один упавший эндпоинт больше не останавливает ботов.

## Current behavior (bug / limitation)

- `TaskPlanner` конструирует **ровно один** клиент: `OpenAICompatibleClient.forProvider(AI_PROVIDER, ...)` + оборачивает в `ResilientLLMClient` (retry/circuit breaker внутри одного провайдера).
- При недоступности провайдера retry исчерпывается → circuit breaker OPEN → `LLMFallbackHandler` отдаёт шаблонный ответ «follow player». Боты формально живы, но тупые.
- Смена провайдера = правка `vasyan-common.toml` + рестарт.
- `VasyanCommands` (status/health) показывает только активного провайдера из конфига.

## Desired behavior

1. Конфиг:
   ```toml
   [llm]
   providerChain = ["opencode-go", "ollama"]
   ```
   Пустая/отсутствующая цепочка = `[AI_PROVIDER]` (обратная совместимость).
2. Сбой запроса (HTTP-ошибка, таймаут, 5xx, пустой ответ) → автоматическое переключение на следующий провайдер цепочки **в рамках одного запроса**.
3. Переключение логируется + уведомление игроку (chat) один раз на переключение, не спам.
4. Возврат: приоритетный провайдер периодически пробуется (cooldown ~60с); успех → обратное переключение с уведомлением.
5. Healthcheck/status команды показывают всю цепочку и активного провайдера. Недоступный `/models` (ollama, #27/#28) не валит healthcheck цепочки.

## Non-goals

- Балансировка нагрузки между провайдерами (только failover).
- Hot-reload цепочки (Forge config reload уже есть; пересоздание клиентов — отдельная задача, не здесь).

## Root causes to investigate (для имплементера)

1. `TaskPlanner.<init>`: жёсткая привязка к одному `baseClient`; поле используется в логах/health.
2. `ResilientLLMClient`: circuit breaker per-provider уже есть — его можно переиспользовать как сигнал «провайдер нездоров» вместо ручных счётчиков.
3. `LLMFallbackHandler` срабатывает когда ВСЕ провайдеры умерли — семантика сохраняется.
4. Ключи/baseUrl/model для каждого провайдера берутся из тех же конфиг-полей (`LLM_BASE_URL`, `LLM_API_KEY`, `LLM_MODEL`) через `LLMProviders.resolveBaseUrl/resolveModel` — проверить, что для двух кастомных провайдеров одновременно хватает одного набора полей (если нет — задокументировать ограничение: chain из пресетов openai/groq/gemini/ollama/lmstudio/opencode-go/custom, где custom может быть один).

## Implementation plan

### T1. Config
- `VasyanConfig`: `ConfigValue<List<? extends String>> PROVIDER_CHAIN` (`providerChain`, default `[]`), комментарий с примером.
- Валидация при чтении: неизвестные id → warn + пропуск; дедуп; пусто → fallback на `AI_PROVIDER`.

### T2. ProviderChainClient (новый класс в `llm/resilience/`)
- `implements AsyncLLMClient`.
- Конструктор: список готовых `AsyncLLMClient` (каждый уже обёрнут в свой `ResilientLLMClient`? — НЕТ: один внешний retry достаточно, вложенные circuit breaker'ы оставить как health-сигнал).
- Логика `sendAsync`:
  - идём по цепочке от текущего индекса;
  - провайдер пропускается, если его circuit breaker OPEN или cooldown ещё не истёк (после неудачи);
  - первый успех → запоминаем активный индекс, возвращаем ответ;
  - все умерли → исключение/фолбэк как сейчас.
- Recovery: если активный ≠ самый приоритетный, раз в `failoverRetrySeconds` (конфиг, default 60) пробуем головной провайдер фоново/при следующем запросе.
- Потокобезопасность: volatile activeIndex, без блокировок на hot path.
- Уведомления: колбэк `Consumer<String>` (чат-сообщение), вызывается только на смене активного провайдера.

### T3. Wiring в TaskPlanner
- Построить клиентов по цепочке, обернуть в `ProviderChainClient`, его — в один общий resilience-слой (retry поверх цепочки НЕ дублировать: retry внутри ResilientLLMClient каждого провайдера уже даёт повторные попытки; внешний слой — только cache+fallback).
- Сохранить доступ к списку клиентов для status-команды.

### T4. Команды/наблюдаемость
- Расширить существующий `/vasyan providers` (не создавать новую команду!): показать цепочку, активного провайдера (может отличаться от головного при failover), состояние circuit breaker'ов каждого члена цепочки; health-проверку гонять по всей цепочке, а не только по `AI_PROVIDER`.
- Chat-уведомления оператору при переключениях (вперёд и назад).

### T5. Тесты
- Юнит: мок 3 провайдеров; сбой первого → второй отвечает; восстановление первого → возврат; cooldown не даёт шторма попыток; пустой chain → поведение как сейчас (один провайдер).
- Behavior (CI): сценарий с двумя эндпоинтами (один мёртвый) — бот продолжает выполнять команды.

## Acceptance criteria (из issue #33)

- [ ] Цепочка задаётся в конфиге
- [ ] Сбой активного → авто-переключение за один запрос
- [ ] Логирование + chat-уведомление о переключении
- [ ] Возврат на приоритетный после восстановления
- [ ] Юнит-тесты: мок 2+ провайдеров, сбой первого, порядок цепочки
- [ ] `/vasyan providers` показывает цепочку и активного (фактического) провайдера
